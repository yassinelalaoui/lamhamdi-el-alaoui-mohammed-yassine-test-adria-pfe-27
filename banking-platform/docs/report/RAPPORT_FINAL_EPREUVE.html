Partie B — Conception et Architecture

1. Architecture Globale du Système

L'architecture cible est articulée autour de microservices autonomes interconnectés via un bus d'événements Kafka et régis par une passerelle Spring Cloud Gateway :

  • Couche Présentation : Client Web SPA (HTML5/Tailwind/React) et bots conversationnels (REST & Telegram).
  • Passerelle & Sécurité : Spring Cloud Gateway (port 8080) validant les jetons JWT Keycloak et assurant le routage dynamique.
  • Services Techniques : Eureka Discovery Server (port 8761) et Spring Cloud Config Server (port 8888).
  • Services Métier :
    • account-service (port 8081) : Gestion des comptes bancaires, isolation du domaine, persistance PostgreSQL, migrations Flyway.
    • transaction-service (port 8082) : Validation du solde, enregistrement des transactions et virements, publication d'événements Kafka.
  • Agentique & IA : ai-assistant (port 8084) interfaçant Spring AI et les outils MCP pour automatiser les requêtes bancaires.
  • Audit & Asynchrone : transaction-consumer (port 8085) journalisant les événements du topic bank.transactions.created.
  • Expérimentation ML : fraud-detection (Python) pour la classification binaire supervisée des fraudes.

2. Séparation Rigoureuse des Couches (Domain-Driven Design)

Conformément aux directives de l'épreuve, les micro-services respectent l'isolation en couches :

├── domain/        -> Entités métier pures, immutables, Value Objects, règles invariantes
├── repository/    -> Interfaces Spring Data JPA / persistance relationnelle
├── service/       -> Orchestration métier, transactions ACID, vérification des plafonds
├── web/rest/      -> Contrôleurs RESTful avec DTOs et validation (@Valid)
├── web/graphql/   -> Contrôleurs GraphQL Query/Mutation mappant sur le même service
└── web/mcp/       -> Outils MCP (@McpTool) exposés pour l'agent IA

2. Communication Inter-Services (OpenFeign) & Tolérance aux Pannes (Resilience4J)

Pour vérifier l'existence et l'état actif d'un compte avant d'enregistrer une transaction, transaction-service utilise un client déclaratif OpenFeign vers account-service :

@FeignClient(name = "account-service", fallback = AccountServiceFallback.class)
public interface AccountServiceClient {
    @GetMapping("/api/accounts/{id}")
    AccountView getAccount(@PathVariable("id") UUID accountId);

    @PatchMapping("/api/accounts/{id}/balance")
    BalanceAdjustmentView adjustBalance(@PathVariable("id") UUID accountId, @RequestBody BalanceAdjustmentRequest request);
}

Un disjoncteur (Circuit Breaker) Resilience4J est configuré : en cas de défaillance ou de latence anormale (> 3s), le disjoncteur bascule sur le fallback et lève AccountServiceUnavailableException, empêchant la cascade de pannes dans le cluster.

Après la persistance réussie d'une transaction, un événement immutable est publié dans le topic bank.transactions.created avec accountId comme clé de partitionnement :

2. Réponses Approfondies aux Questions d'Analyse Métier

Question 1 : Pourquoi l’accuracy seule est-elle insuffisante ?
En présence de classes hautement déséquilibrées (ex. 96.42% de légitimes pour 3.58% de fraudes), un algorithme trivial qui prédirait constamment la classe majoritaire (« non-fraude ») atteindrait 96.42% d'accuracy tout en ayant un rappel de 0%, laissant s'échapper 100% des fraudes réelles. L'accuracy est trompeuse car elle est dominée par la classe majoritaire.

Question 2 : Quel compromis existe entre faux positifs et fraudes non détectées ?
Un Faux Positif (FP) bloque injustement un client légitime, générant de la friction et des coûts d'investigation manuelle pour le support client. Un Faux Négatif (FN) laisse passer une fraude, causant une perte financière directe (remboursement obligatoire) et un préjudice réputationnel. La banque cherche à maximiser le rappel pour éliminer les FN tout en maintenant les FP sous un ratio tolérable.

Question 3 : Quel est l’effet possible d’une diminution du seuil de décision ?
Abaisser le seuil de décision (ex. de 0.50 à 0.25) accroît la sensibilité du système : le rappel augmente (moins de fraudes manquées), mais la précision baisse et le volume de faux positifs augmente mécaniquement, sollicitant davantage les équipes d'analyse ou les mécanismes d'authentification forte (OTP/biométrie).

Question 4 : Pourquoi privilégier une validation temporelle sur des données bancaires réelles ?
Une séparation aléatoire standard crée une fuite temporelle d'information (data leakage) en utilisant des comportements futurs pour prédire le passé. En milieu bancaire, les fraudeurs adaptent continuellement leurs stratégies (concept drift) et les volumes varient selon la saisonnalité. Une validation temporelle (ex. TimeSeriesSplit : train sur les mois 1 à N, test sur le mois N+1) reproduit fidèlement la réalité de mise en production.
